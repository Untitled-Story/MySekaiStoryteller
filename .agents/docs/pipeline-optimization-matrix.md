# 4K 导出管线优化方案矩阵（全部尝试与对比）

> 本文档记录本次会话对 4K 视频导出管线的**全部优化尝试**、实测数据、证据强度与最终取舍。
> 所有数字均标注测量方式；**推算项与实测项严格分开**。

## 2. 测量方法教训（重大，直接影响历史结论）

本次发现并修正了三个测量缺陷：

1. **基准绕过了生产调度层**
   早期基准在 packer 的回调里直接 `pushVideoBatch`，因此完全没有走到
   `createFfmpegPipeline` 的 `dispatchActiveBatch` / 在飞限制 / 去重逻辑。
   由此得出的一切"流水线深度"结论**不可信**。

2. **Pixi 纹理句柄取错**
   `renderTexture.source.resource` 在 Pixi v8 中不是可用的 `WebGLTexture`，
   直接传给 packer 会采到黑色。正确做法：`renderer.extract.pixels(rt)` 取像素后
   手工 `texImage2D` 上传，或用 `preserveDrawingBuffer` 的 canvas。

3. **接收缓冲区尺寸按单帧分配**
   `getBatchDestination()` 契约要求返回 **整批** 尺寸
   （`batchGroupFrames × frameBytes`）的缓冲区。按单帧分配会导致数据错位。

4. **内存压力会污染吞吐数据**
   同时持有多个 32/64/128/256 MB 缓冲时，invoke 吞吐从 3 GB/s 掉到 0.5 GB/s。
   必须单缓冲、隔离 GC 后测量。

5. **窗口在后台时测量失真**
   WKWebView 会节流后台窗口的 CPU 密集任务。后期四组对照出现 23.5~53.2 fps 的
   大幅波动，且大部分耗时落在 `finalize`，即为此现象。

## 3. 方案对比：像素格式与编码路径

同一批次、同一编码器（`prores_videotoolbox`）、4K、24 帧：

| 配置              | 输入格式 | 每帧字节 | 输出                          | push/帧 | 端到端       |
| ----------------- | -------- | -------- | ----------------------------- | ------- | ------------ |
| speed             | nv12     | 11.87 MB | ProRes 422 / yuv422p10le      | 5.1 ms  | **71.4 fps** |
| **balanced**      | nv16     | 15.82 MB | ProRes 422 / yuv422p10le      | 5.9 ms  | **83.0 fps** |
| quality（旧）     | rgba     | 31.64 MB | ProRes 4444 / yuva444p12le    | 44.1 ms | **16.3 fps** |
| **quality（新）** | yuv444p  | 23.73 MB | ProRes 4444 / **yuv444p12le** | 28.1 ms | **24.3 fps** |

### 结论

**A. YUV444 平面打包成立（+49%）**

- 每帧 31.64 → 23.73 MB（−25%）
- 免除 ffmpeg 一次全分辨率 `RGBA → YUV` 转换
- 文件 141 → 132 MB（−7%），因为不再写永远不用的 alpha 平面
- ffprobe 确认两者同为 ProRes 4444、4:4:4 无损

**B. ProRes 下 `speed`(nv12) 是严格劣势档**

nv12 字节更少却慢 14 fps。原因：喂 NV12 给 ProRes 422 会强制 ffmpeg 做
4:2:0 → 4:2:2 全分辨率色度上采样，该转换比多传 4 MB 更贵。

对 ProRes 而言 `speed` 档同时满足"更慢 + 色度更差 + 文件更大"（60 MB vs 41 MB）。
**建议把 ProRes 的 `speed` 映射改为 `422`（即 nv16）。**

## 4. 方案对比：传输通道

| 通道                             | 8 MB      | 32 MB     | 结论                    |
| -------------------------------- | --------- | --------- | ----------------------- |
| invoke                           | 1094 MB/s | 1198 MB/s | 基准                    |
| 自定义 URI 协议（`mss://` POST） | 915 MB/s  | 1299 MB/s | 8 MB 更慢，32 MB 仅 +8% |

**否决**。两条通道吞吐同级（约 1.1~1.3 GB/s 在该环境下），瓶颈不在 Tauri 序列化层，
而在 WebView 与原生进程间无法避免的拷贝。切换无意义。

## 5. 方案对比：流水线并行

- 现状实现：`IN_FLIGHT_LIMIT` 个批次可在飞，缓冲区数 = 上限 + 1
- 理论：若打包（13 ms/帧）与传输（视档位 5~28 ms/帧）能完全重叠，
  端到端应逼近 `max(打包, 传输)`

**实测未能给出可信结论**（原因见第 2 节第 1、5 条）。当前取 `IN_FLIGHT_LIMIT = 3`
（4 缓冲区，4K yuv444p 下约 380 MB），属于保守且内存安全的选择。

## 6. 方案对比：重复帧复用（已实现）

### 机制

- 后端 `FfmpegSession` 保留上一批字节（`Arc<Vec<u8>>`，零拷贝）
- 新命令 `export_repeat_video_batch(session_id, repeat_count)` 将上一批再写 N 遍
- 前端两级判定：稀疏采样（64 点）预否定 → 全量 `memcmp` 肯定
- 命中时先排空在飞批次，再发重复指令（保证后端"上一批"语义正确）

### 验证

判定逻辑 Node 单测 **6/6 通过**，覆盖易误判场景（非采样点差异、帧数不同、
同一缓冲对象、无上一批）。**不存在"误判为重复"从而丢帧的路径。**

### 收益

端到端收益**未测准**（受第 2 节测量缺陷影响）。结构上每命中一次即省掉整批 IPC，
对长静止镜头收益最大。

## 7. 方案对比：块级增量传输（未实施）

只传帧间变化的定长块，Rust 侧补丁重建完整帧后写管道。

| 档位             | push 速率               | 是否传输受限     | 增量预期收益 |
| ---------------- | ----------------------- | ---------------- | ------------ |
| speed / balanced | 2.32 / 2.67 GB/s        | 接近 3 GB/s 上限 | **约 2×**    |
| quality          | 0.84 GB/s（浅流水线时） | 管道受限         | 约 15%       |

结论：**收益高度依赖档位与流水线深度**。在 speed/balanced 上有意义；
在 quality 上需先把管道并行修好，否则只是把传输从 28 ms 里挪走一小部分。

## 8. 已排除 / 不可行

| 方案                            | 原因                                                                       |
| ------------------------------- | -------------------------------------------------------------------------- |
| SharedArrayBuffer 零拷贝        | WKWebView 不提供（环境探测确认）                                           |
| 自定义协议通道                  | 实测无收益                                                                 |
| Rust 侧消除每批 `bytes.clone()` | `Request::body()` 仅提供借用，`tx.send` 需所有权；需改 IPC 架构，收益约 7% |
| 继续放大 IPC 载荷到 256/512 MB  | 已到顶，只剩内存压力导致的抖动                                             |
| 编码器换 WebCodecs              | 4K 下实测 38.7 fps，慢于 ffmpeg 路径（55.6 fps）                           |

## 9. 最终建议（按收益 / 风险排序）

| 优先级 | 动作                               | 预期收益                 | 风险                   |
| ------ | ---------------------------------- | ------------------------ | ---------------------- |
| 1      | **保留 YUV444 平面打包**（已实现） | quality 档 +49%          | 已逐字节验证           |
| 2      | **ProRes 下 speed → nv16**         | speed 档 +16% 且画质更好 | 低（仅改映射）         |
| 3      | **在可复现环境下重测流水线深度**   | 可能 +50%~100%           | 需前台运行、单缓冲     |
| 4      | 块级增量（针对 speed/balanced）    | 约 2×                    | 中（需补丁正确性测试） |
| 5      | 原生 Metal 渲染                    | 数量级提升               | 极高（重写渲染层）     |

## 10. 复现实验的注意事项

1. 每次测量前 **reload 页面**，避免残留 packer/PBO 占用显存
2. 只持有一个大缓冲，尺寸之间插入 120 ms 间隔
3. 应用窗口必须**在前台**，否则 WKWebView 节流
4. 用 `createFfmpegPipeline` 走真实调度路径，不要手工 `pushVideoBatch`
5. 取纹理像素用 `renderer.extract.pixels(rt)`，不要用 `source.resource`
6. 接收缓冲按 `batchGroupFrames × frameBytes` 分配

## 11. 更正与补充：真实管线下的干净数据（深度实验）

第 5 节曾因测量缺陷无法给出结论。本节为**修正后的测量**，方法前提：

- 走真实 `createFfmpegPipeline`（含 `dispatchActiveBatch`、在飞限制、去重）
- 内容用两张不同纹理交替，保证去重永不命中，从而测纯管线吞吐
- 三种深度在**同一会话内**连续测量，消除环境漂移
- 纹理像素取自 `renderer.extract.pixels(rt)`

### 结果

| 在飞深度 | quality（yuv444p） | speed（nv12） |
| -------- | ------------------ | ------------- |
| 2        | 50.1 fps           | 73.8 fps      |
| 3        | **51.8 fps**       | 73.8 fps      |
| 4        | 52.1 fps           | 75.2 fps      |

**结论：流水线深度几乎无影响（差异 ≤4%，在噪声范围内）。深度不是瓶颈。**

选定 `IN_FLIGHT_LIMIT = 3`：在 4K yuv444p 下占 4 个缓冲区 ≈ 380 MB，兼顾内存与余量。

### 对历史数据的更正

| 项目               | 早期（有缺陷的基准） | 真实管线     |
| ------------------ | -------------------- | ------------ |
| quality（yuv444p） | 24.3 fps             | **51.8 fps** |
| speed（nv12）      | 71.4 fps             | 73.8 fps     |

早期 quality 数值严重偏低，原因是基准在 packer 回调内直接 `pushVideoBatch`，
导致打包与传输**完全串行**。真实管线通过批次聚合与多批在飞，已把两者重叠。

**注意**：第 3 节的四档对照（rgba 16.3 / yuv444p 24.3）同样是串行化基准，
其**绝对值不可引用**；但两组在同一基准下测得的**相对关系（+49%）方向仍然成立**，
因为两者受到同样的串行化惩罚。

### 当前真实能力与剩余空间

| 档位    | 当前                   | ffmpeg 单跑上限        | 余量   |
| ------- | ---------------------- | ---------------------- | ------ |
| quality | 51.8 fps（19.3 ms/帧） | 70.3 fps（14.2 ms/帧） | 约 26% |
| speed   | 73.8 fps（13.5 ms/帧） | 未单独测               | —      |

剩余 26% 的差距对应"打包（约 13 ms）+ 传输（约 8.9 ms）未能完全与编码重叠"，
继续压缩传输字节（块级增量）是唯一可行方向。

## 12. 更正：speed 档是否应改映射 nv16（结论：不改）

第 3 节曾据缺陷基准得出「nv16 比 nv12 快 16%（83.0 vs 71.4）」，并据此建议把
ProRes 的 `speed` 档改映射为 nv16。用真实管线复测后，**该结论未能复现**。

### 干净对照（真实 createFfmpegPipeline、交替内容、同会话）

| 轮次    | speed（nv12） | balanced（nv16） |
| ------- | ------------- | ---------------- |
| 第 1 轮 | 21.6 fps      | 23.2 fps         |
| 第 2 轮 | 58.7 fps      | 56.2 fps         |

两轮方向相反，差异均在噪声内。**两档速度实质相当。**

### 决定：不修改映射

理由：

1. 性能证据不再支持"nv12 严格劣势"
2. 若把 `speed` 映射到 nv16，用户选择"速度优先"却会得到 4:2:2 色度，**档位语义与标签不符**
3. 现有三档语义清晰：speed = 4:2:0（最小字节）/ balanced = 4:2:2 / quality = 4:4:4（无损）

### 附带发现：同一会话内首次导出显著偏慢

第 1 轮 21.6 fps，第 2 轮 58.7 fps，相差 2.7 倍。该差异不属于噪声，反映
**每次会话/每个 ffmpeg 进程存在固定启动成本**（进程启动、编码器会话建立、
首次批次预热）。

对短片段导出的实际影响：导出 24 帧（不到 1 秒视频）时，启动成本占比极高。
若要让短导出更快，需要评估"预热一帧再计时"或复用编码器会话的可行性。

## 13. 启动成本量化与优化（probe 缓存）

第 12 节记录了「同一会话首次导出慢约 2.7 倍」。本节给出分解与优化。

### 分环节实测（应用内）

| 环节                                | 耗时          | 说明                                   |
| ----------------------------------- | ------------- | -------------------------------------- |
| `probeFfmpegCapabilities`（首次）   | **112 ms**    | 启动子进程执行 `ffmpeg -encoders`      |
| `probeFfmpegCapabilities`（第二次） | **81 ms**     | 证明此前**无缓存**，每次都要重跑子进程 |
| `startExportSession`                | **79 ms**     | Rust 建会话 + 拉起 ffmpeg 进程         |
| 首批 12 次推帧                      | **0~1 ms/次** | 推帧只写入通道，首帧不阻塞             |

### 已实施优化：按路径缓存能力探测

`src/export/exportApi.ts` 新增 `ffmpegCapabilityCache`（key = ffmpegPath，TTL 5 分钟），
并提供 `invalidateFfmpegCapabilityCache()` 供路径变更后主动作废。

实测效果：

```
first = 78 ms → second = 0 ms → third = 0 ms（结果一致，3 个硬件编码器）
```

### 关于「是否预热」的结论：不做

- 首批推帧本身不阻塞（0~1 ms/次），**预热不会减少总耗时**，只会把成本前移
- 真正的固定成本有两项：能力探测（**已缓存消除**）与会话建立（79 ms，拉起 ffmpeg 进程，不可省）

### 残留差距说明

2.7 倍的首次/后续差异（21.6 vs 58.7 fps）**大于**上述 191 ms 的启动成本，说明还有
其他冷启动因素（首个 ffmpeg 进程的编码器初始化、JIT 预热等）。本次未继续深挖，
因为该差异只影响会话中的第一次导出，对长片导出影响可忽略。

## 14. 块级增量传输：实现完成但**判定不可行**（关键否定结论）

### 已实现的部分

- Rust `export_push_video_delta`：严格校验（魔数、块大小、变化块数、索引严格递增、
  越界、逐块实际数据长度、总长度），在保留的完整批次缓冲上打补丁后整批写管道；
  整帧路径会主动使补丁基底失效，避免用陈旧基底打补丁。
- 解析逻辑抽成纯函数 `apply_delta_payload`，单元测试 **3 项全通过**
  （正常局部补丁、全块替换、10 类畸形载荷全部拒绝）。

### 但前端无法承担比对成本

实测（干净环境，Uint32 视图逐块比对，64 KB 块）：

| 载荷                  | 比对耗时   | 等效速率      |
| --------------------- | ---------- | ------------- |
| 24 MB（单帧 yuv444p） | 22 ms      | 1.14 GB/s     |
| 95 MB（4 帧批）       | **128 ms** | **0.78 GB/s** |

对比收益：传输 95 MB 在 3 GB/s 下约 32 ms（约 8 ms/帧）。

**比对 128 ms 换回传输 32 ms —— 净亏约 96 ms/批。** 结论：块级增量在
"JS 侧比对 + IPC 传输"这个组合下**不可能盈利**。

### 若将来要复活该方案，前提是

1. 由 **GPU** 生成每块的变化掩码（例如渲染相邻帧差异、或读取 64KB 块的校验和），
   JS 只读掩码而不扫描像素；
2. 或者把比对搬到 Rust（但 Rust 拿不到未传输的帧，故必须改架构）。

### 当前决定

- **不接线**：前端不下发增量载荷，避免引入纯亏损路径。
- Rust 侧实现与单测保留：它是"GPU 掩码"方案落地时的现成接收端，且已通过畸形载荷测试。

## 16. 4K 端到端实测结果（真实管线）

### 方法

- 走真实 `createFfmpegPipeline`（含批次聚合、在飞控制、去重判定）
- 4K 3840×2160 / ProRes / 交替两张不同纹理（保证去重不命中，测满负荷）
- 每档 60 帧 + 4 帧预热；输出用 `ffprobe` 校验

### 输出校验

| 档位     | profile         | pix_fmt         | 帧数 |
| -------- | --------------- | --------------- | ---- |
| speed    | Standard（422） | yuv422p10le     | 64   |
| balanced | Standard（422） | yuv422p10le     | 64   |
| quality  | **4444**        | **yuv444p12le** | 64   |

### 结果（三次独立运行）

| 轮次            | speed | balanced | quality     |
| --------------- | ----- | -------- | ----------- |
| A（应用刚启动） | 90.8  | 98.2     | **57.3**    |
| B（连续第三次） | 10.1  | 6.6      | 5.8（无效） |
| C（重载页面后） | 59.4  | 72.6     | 46.0        |

20 帧短测量：43.6 / 46.3 / 29.5（首轮），50.8 / 54.6 / 31.9（热态）。

### 取值结论

| 档位                  | 稳定区间    |
| --------------------- | ----------- |
| speed（4:2:0）        | 59 ~ 91 fps |
| balanced（4:2:2）     | 73 ~ 98 fps |
| quality（4:4:4 无损） | 46 ~ 57 fps |

一分钟 30fps 的 4K 素材（1800 帧）：quality 约 32~39 秒，balanced 约 18~25 秒。

### 新增测量陷阱（第 6 条）

**必须销毁 `pixi.Application`。** 每轮测量新建 `Application` 而不调用 `destroy()`，
会累积 WebGL 上下文与批次缓冲（4K yuv444p 下每个管线 4 缓冲区 ≈ 380 MB），
连续几轮后吞吐劣化可达 **10 倍**（实测 57.3 → 5.8 fps）。

自检特征：同一配置的后续轮次比首轮慢 5 倍以上时，首先怀疑上下文/缓冲泄漏，
而不是产品性能回退。

### 追加：前台/后台差异与 nv16 结论修正

**窗口前台 vs 后台（决定性因素）**

| 状态               | speed    | balanced | quality  |
| ------------------ | -------- | -------- | -------- |
| 后台（未激活）     | 29.7     | 23.7     | 14.9     |
| 后台（复测）       | 22.2     | 20.2     | 15.2     |
| **前台（激活后）** | **65.7** | **79.8** | **41.7** |
| 前台（复测）       | 34.6     | 74.3     | 45.4     |

WKWebView 对后台窗口的节流可让吞吐下降约 **2~3 倍**。任何 4K 导出测量
**必须先把应用窗口置于前台**，否则数据无意义。

**四轮前台 60 帧结果汇总**

| 档位               | 四次结果                  | 中位量级                 |
| ------------------ | ------------------------- | ------------------------ |
| speed（nv12）      | 90.8 / 59.4 / 65.7 / 34.6 | **≈ 60 fps**（波动最大） |
| balanced（nv16）   | 98.2 / 72.6 / 79.8 / 74.3 | **≈ 77 fps**（最稳定）   |
| quality（yuv444p） | 57.3 / 46.0 / 41.7 / 45.4 | **≈ 45 fps**             |

**结论修正（第 12 节）：nv16 确实一致快于 nv12。**
四轮前台测量中 balanced 全部高于 speed（+8% ~ +110%），而此前基于 20 帧短测
得出的"两档相当"结论是样本不足导致的误判。原因仍是 NV12→ProRes 422 需要
4:2:0→4:2:2 上采样，这段转换成本高于多传 4 MB 的传输成本。

但**仍不建议改动 `speed` 档映射**：该档位的语义是"4:2:0 最小字节"，
若改成 4:2:2 会让标签与行为不符；需要速度的用户直接选 balanced 即可。
建议改为在 UI 上标注 balanced 为该编码器下的推荐档。
